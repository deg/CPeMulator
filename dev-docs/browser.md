# The browser build

CPeMulator runs in a web page as well as in a terminal, from the same emulator code.
The live site is <https://cpemulator.degel.com/>. This document explains how the
browser version is put together, how to build and test it, and the decisions behind
it. The work is tracked under the epic `cpemu-y1b` (boot CP/M in the browser).

## The big picture

```
  web/www/main.js   the page: an xterm.js terminal, the control panel,
       |            the animation-frame loop, saving the disk (IndexedDB)
       |  wasm-bindgen glue (web/www/pkg/, generated by web/build.sh)
       v
  crates/web        cpemu-web: a thin wasm-bindgen wrapper (`Emulator`) and the
       |            bundled DRI utilities for a fresh drive A:
       v
  crates/cpemu      the emulator library, shared with the CLI:
       |              session.rs   Session: a CP/M machine run in slices; BufferConsole
       |              keys.rs      typed-key translation (Delete, arrows)
       |              terminal.rs  TVI-950 -> ANSI output translation
       |              bios.rs, disk.rs, cpm22.rs, ...
       v
  crates/cpu        the Z80 core (unchanged; it always compiled for wasm)
```

The code is compiled to **WebAssembly** (the `wasm32-unknown-unknown` target): a
compact binary format every modern browser runs at close to native speed. The whole
module is about 140 KB, most of it the bundled CP/M utilities.

## The one hard problem: never block

The CLI owns its thread. When CP/M waits for a key, the CLI can block in a read, or
sleep. A web page can't do either. JavaScript runs one task at a time on the page's
thread, so a call that blocks freezes the tab, and the keystroke it is waiting for
can never be delivered, because delivering it is another task.

Two pieces of the existing design make this easy:

1. **CONIN never blocks.** When a program asks the BIOS for a key and none is waiting,
   the BIOS does not wait; it jumps back to its own entry point
   (`TrapAction::Jump`, in `bios.rs`). A program waiting for input is therefore just a
   CPU spinning on one address. That is visible from outside, and it can be stopped
   between any two instructions.
2. **[`Session::run`](../crates/cpemu/src/session.rs)** runs the machine for a budget
   of CPU cycles and returns. It returns early with `Idle` when the CPU is at CONIN
   with no key queued.

So the page's loop, once per animation frame (about 60 a second), is:

1. run about one frame's worth of cycles: at 4 MHz, 4,000,000 / 60, about 66,667;
2. write whatever CP/M printed to the terminal;
3. if the result was `Idle`, stop asking for frames until the user types.

An idle page costs nothing, and a program that busy-waits (a game polling the
keyboard with CONST) is just cut into frame-sized slices, so the tab stays
responsive. **No Web Worker is needed**, unlike in nscheme's browser build, where an
evaluation can't be interrupted.

The cycle budget is also the speed control. Real time decides how many cycles a
frame gets (the "Speed" menu: 2, 4, 8, 25 MHz). "Max" instead runs for about 12 ms
of each frame, as fast as the host can go. The CLI's `Throttle`, which sleeps, is
not used.

## What had to change in the shared library

Most of the library compiled for wasm as it was. The changes were:

| Problem | Fix |
|---------|-----|
| `crossterm` (raw terminal mode) doesn't compile for wasm32 | A native-only dependency; the `console` module (`TerminalConsole`) is compiled only for native targets. |
| `std::time::Instant` and `thread::sleep` compile for wasm32 but **panic when called** | `throttle` is native-only. The browser paces itself per frame. |
| The key translation (Delete to Backspace, arrows to WordStar keys) lived inside the native console | Moved to `keys.rs`, shared. xterm.js sends the same bytes as a real terminal (`ESC [ A` for Up, `0x7F` for Backspace). |
| The CCP/BDOS bytes and the text-file `^Z` rule lived in `main.rs` | Moved into the library (`cpm22.rs`, `disk::terminate_text_file`). |
| The interactive run loop lived in `main.rs` and slept | `session.rs`: the loop that runs in slices, plus `BufferConsole`, a console that is two byte queues. |

`make check` includes `cargo check -p cpemu --lib --target wasm32-unknown-unknown`, so
a native-only dependency can't slip back in unnoticed. Compiling isn't the same as
working, though: the panics above only show when the code runs. That is why the
smoke test boots the real wasm module (below).

Following nscheme's rule (its ADR 0012), browser behaviour lives in the library,
where native `cargo test` covers it. `Session` is plain Rust with no browser
dependency, and its tests boot CP/M, type `DIR`, upload a program and run it.

## The wrapper crate: `crates/web`

`cpemu-web` exposes one class to JavaScript, `Emulator`:

| Method | Does |
|--------|------|
| `new Emulator()` | Cold-boot with a fresh 8 MB disk holding the bundled utilities. |
| `Emulator.fromImage(bytes)` | Cold-boot from a saved drive-A: image or a `.dsk` file. |
| `run(cycles)` | Run; returns `"running"`, `"idle"`, `"halted"`, `"stopped"` or `"illegal XX"`. |
| `typeBytes(bytes)` / `takeOutput()` | Keys in; ANSI screen output out. |
| `putFile(name, bytes)` | Put a file on A: (replacing one of that name), then warm-boot so CP/M sees it. |
| `diskImage()` / `diskChanges()` | The image to save, and a counter that says whether it changed. |
| `files()` / `readFile(name)` | The file list, and one file's contents. |
| `warmBoot()` | Like `^C` at the prompt. |
| `inProgram()` | Whether a program is running (so an upload or reset would end it). |
| `putZip(bytes)` | Put every file in a `.zip` on A: (folders flattened); returns which went on and which were skipped, and why. |

It is a separate crate because the glue that `#[wasm_bindgen]` generates uses
`unsafe`, which the `cpemu` crate forbids. `wasm-bindgen` is pinned to an exact
version, because the `wasm-bindgen` command-line tool that post-processes the
`.wasm` must be the same version.

### Why uploading warm-boots

BDOS keeps an in-memory map of which disk blocks are in use, built when it first
touches a drive. If the host adds a file behind its back, the next file CP/M writes
can land on the new file's blocks. A warm boot (what `^C` at the prompt does)
reloads the CCP and BDOS, and the BDOS rebuilds that map from the directory. The cost
is that an upload ends any program that is running, losing whatever it hasn't saved.
So the page asks first, but only when a program is running: `Session::in_program`
(the wrapper's `inProgram()`) is true from the moment the CCP jumps to `0100h` to
start a program until the CCP makes its next BDOS call, which it does at once to print
the prompt. (Every BDOS call leaves its caller's address on the stack, which says
whether the CCP or a program is asking.) At the `A>` prompt nothing can be lost, so
the page doesn't ask there. Reset asks the same way.

## The page: `web/www`

- `index.html` and `style.css`: the header, the control panel (one wrapping row of
  button groups above the terminal), the file list, the terminal, the status line.
- `main.js`: boot, the frame loop, the keys, the disk.
- `vendor/xterm/`: xterm.js 6.0.0, the terminal widget, copied unchanged with its MIT
  license (`VERSION` records the source and hash). It is vendored rather than loaded
  from a CDN so the site depends on no third party at run time and works offline.

The terminal is a fixed 80x24, like the terminals CP/M software was written for. On
a narrow screen it scrolls sideways rather than shrinking.

### Keys the browser keeps

On Windows and Linux, browsers don't let a page see Ctrl-W, Ctrl-T or Ctrl-N (close
tab, new tab, new window), and WordStar and Turbo Pascal use all three. (macOS uses
Cmd for those, so Ctrl works.) The **Ctrl** button is a sticky modifier: click it,
and the next key typed is sent as its control code. It also gives phones, which
have no Ctrl key, every control code. **Esc** and **^C** are buttons too.

### Saving the disk, and why the download is the real copy

Drive A: is saved in the browser's IndexedDB under the key `A`, whenever
`diskChanges()` differs from its value at the last save: at most once a second
while a program runs, and immediately when CP/M goes idle or the tab is hidden.
Each save writes the whole image, a cost small enough not to optimise: for the
8 MB disk a fresh page starts with (the desktop version's default too), an
IndexedDB save measured about 5 ms in Chromium, and 0.2 ms for a 241 KB floppy.
Saving only the changed parts of the image would be the next step if that ever
mattered. A disk saved as a floppy by an earlier version still boots, since the
format is detected from the image's size. On the next visit the page boots from it. Nothing leaves the browser.

**Browsers treat that storage as disposable.** Safari deletes a site's data after
about seven days of use without a visit. Any browser may clear it when the disk
runs low, when history is cleared, or when a private window closes. So the page:

- makes **Download disk** the prominent button: it saves the image as a `.dsk`
  file, which **Upload** accepts back and the CLI mounts (`cpemu --disk=cpemulator-A.dsk`);
- remembers whether the disk has changed since it was last downloaded, and says
  so in the status line ("changed since your last Download disk") until it is
  downloaded again. That flag is kept in `localStorage`, not IndexedDB, because
  it writes synchronously: an IndexedDB write started by the Download click is
  lost if the tab closes or reloads a moment later;
- asks the browser to keep the data (`navigator.storage.persist()`) the first
  time the disk changes, which is when there is something to lose. The browser
  may refuse.

A fresh disk and an uploaded `.dsk` count as backed up, since the user can't lose
them. **Fresh disk** (in the file list) starts over. If storage is unavailable
(a private window, blocked site data), the page still works and says it isn't
saving. The chosen speed is kept in `localStorage`.

### Uploading a `.zip`

Most CP/M software is distributed zipped, so an uploaded or dropped `.zip` is
unpacked straight onto A: (`crates/web/src/unzip.rs`, using the `zip` crate). Its
folders are flattened, since a CP/M disk has none, and folder entries and macOS's
`__MACOSX` files are dropped. A member that can't go on the disk (an unreadable or
encrypted member, a name CP/M can't type, a full disk) is reported in the status
line, and the rest still goes on.

Many CP/M archives were zipped in the DOS era with PKZIP 1.x's methods, Shrink and
Implode (Zork's and MBASIC's are imploded). A reader that handles only modern
deflate rejects them, so the `zip` crate is built with its `legacy-zip` feature,
plus deflate on the pure-Rust `zlib-rs` (which builds for wasm), and nothing else.
That roughly doubled the `.wasm`, to about 420 KB, or 175 KB as served compressed.
An ignored test checks the legacy methods against the archives `make setup`
downloads, which aren't ours to commit: `cargo test -p cpemu-web -- --ignored`.

## What a fresh disk holds, and why

Only software we may redistribute: Digital Research's own CP/M 2.2 utilities (PIP,
STAT, ED, ASM, LOAD, DDT, DUMP, SUBMIT, XSUB) and `DUMP.ASM`, DRI's sample source, so
`ASM DUMP` / `LOAD DUMP` / `DUMP DUMP.COM` works as a first program. They come from
the Unofficial CP/M Web Site's copy of the DRI distribution disk and are vendored in
[`third-party/cpm22/utilities/`](../third-party/cpm22/utilities/NOTICE.md) with
their hashes, under the same grant as the CCP and BDOS. Zork, Turbo Pascal, WordStar
and the rest are not hosted. Visitors upload their own (bead `cpemu-kb9`).

## Building, running and testing

One-time setup:

```bash
rustup target add wasm32-unknown-unknown
cargo install wasm-bindgen-cli --version 0.2.130 --locked   # the version crates/web pins
```

Then:

| Command | Does |
|---------|------|
| `make web` | Build into `web/www/pkg/` (`web/build.sh`; `--dev` for an unoptimized build). |
| `make web-serve` | Build, then serve at <http://localhost:8000/>. Browsers won't load `.wasm` from a `file://` URL. |
| `make web-smoke` | Build, then boot the module in Node (`web/smoke.mjs`): boot to `A>`, run `DIR`, upload and run a program, save and restore the disk, and check errors arrive as JavaScript errors, not traps. |

The built `pkg/` is never committed.

## Deployment

`.github/workflows/pages.yml` builds, runs the smoke test, and publishes `web/www`
to GitHub Pages on every push to `main` that touches the code or the page (or by
hand from the Actions tab). The custom domain `cpemulator.degel.com` (a DNS CNAME to
`deg.github.io`) is set in the repository's Pages settings. A workflow-built site
ignores a `CNAME` file. Pages must be enabled once, with "GitHub Actions" as its
source.

## Not in the browser (yet)

- **The debug monitor** (Ctrl-\\ in the CLI). Its prompt reads a line with a blocking
  read. A browser debugger is bead `cpemu-q61`, in Phase 2 (epic `cpemu-81c`).
- **More drives.** The page mounts only A:. `Session` already takes extra drives.
